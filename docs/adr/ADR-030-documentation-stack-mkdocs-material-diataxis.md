# ADR-030: Documentation Architecture and Stack Selection (MkDocs Material, Griffe, Diátaxis)

## Status
Accepted

## Context
As the Enterprise World Model Engine expanded across Rounds 1 and 2 (`P01`–`P16`), the documentation suite grew to over 90 pages spanning conceptual foundations, formal feature specifications, Architecture Decision Records, and task-oriented user guides.

However, the existing documentation presented several critical architectural deficiencies:
1. **Hand-Written API Drift**: The existing `docs/api/reference.md` was manually maintained, omitting over 80% of newly introduced public protocols, submodules, and classes, creating severe documentation drift against the active codebase.
2. **Cognitive Navigational Ambiguity**: Documentation pages mixed pedagogical tutorials, recipes, deep architectural explanations, and technical reference material without a unified structural taxonomy.
3. **Execution Gaps**: Example workflows in documentation lacked an automated execution verification gate, risking silent snippet obsolescence.
4. **Tooling Evaluation**: We evaluated two industry-standard documentation architectures:
   - **Option A (MkDocs Material + mkdocstrings/Griffe + mike)**: Markdown-first authoring, high-velocity build times, rich Material theme with dark/light mode toggles, native AST docstring parsing with Griffe, and native version management via `mike`.
   - **Option B (Sphinx + PyData Theme + numpydoc + sphinx-gallery + MyST)**: Scientific Python standard stack featuring `sphinx-gallery` script execution and cross-project intersphinx mapping.

### Migration Cost & Risk Analysis
- **Sphinx Migration Cost (High / Risky)**: Migrating 90+ existing pages to Sphinx/reST/MyST would require massive syntax conversion for pymdownx superfences, custom mermaid diagrams, admonitions, and material tabs. This would introduce significant risk of broken internal links, syntax failures, and substantial build overhead (>60s vs <5s).
- **MkDocs Material Preservation (Low Cost / High Return)**: MkDocs Material with `mkdocstrings[python]` (powered by Griffe) provides Astral/FastAPI/Pydantic-tier aesthetics and authoring ergonomics. Griffe parses type annotations directly from AST, enforcing strict signature alignment without redundant type declarations in docstrings.

## Decision
1. **Retain and Modernize MkDocs Material**: We adopt **MkDocs Material** augmented with **`mkdocstrings[python]` (Griffe)**, **`mike`**, **`mkdocs-gen-files`**, and **`mkdocs-literate-nav`** as the official documentation engine.
2. **Adopt the Diátaxis Documentation Framework**: Restructure the entire documentation site into the four canonical Diátaxis quadrants:
   - **Tutorials (Learning-Oriented)**: Guided, step-by-step lessons for newcomers (e.g., *Your First World Model*, *Simulating Counterfactual Decisions*, *Executed Example Gallery*).
   - **How-To Guides (Problem-Oriented)**: Practical, recipe-driven instructions for practitioners (e.g., *Phase-Aware Constraints*, *Event-Sourced Trajectory Replay*, *Distributed Monte Carlo*, *DoE Sweeps*, *Co-Simulation with FMI*).
   - **Reference (Information-Oriented)**: Dry, technical specifications (Automated API Reference generated directly from docstrings via `mkdocstrings`, JSON Schemas, CLI Reference, SemVer Stability Policy, Architecture Decision Records).
   - **Explanation (Understanding-Oriented)**: Conceptual and philosophical discussions (Causal Epistemology, Uncertainty & Rollouts, Decision-Grade Evaluation, Zero-LLM Simulation Kernel, World Models vs. World Foundation Models).
3. **Automated API Reference Generation**: Delete the hand-written `docs/api/reference.md` and replace it with modular, autogenerated API pages organized by engine subsystem, populated directly from Python source code docstrings.
4. **Google Docstring Convention**: Enforce the **Google docstring format** across all public modules. Type annotations must live exclusively in Python signatures and never be duplicated in docstrings. Enforce this via Ruff's `pydocstyle` rule set (`convention = "google"`).
5. **Executed Example Gallery & Snippet Verification Gate**: Provide an executed gallery showcasing verified terminal outputs, comparison tables, and systemic trace artifacts. Enforce an automated continuous integration test gate (`scripts/test_doc_snippets.py`) ensuring zero snippet drift.
6. **Versioned Documentation via Mike**: Configure `mike` with default alias `stable`, tracking `latest` (development) and archived version tags.

## Consequences
### Positive
- **Zero Syntax Regressions**: All 90+ existing Markdown files, Mermaid diagrams, and mathematical expressions remain intact and valid.
- **Drift-Free API Documentation**: Public API documentation updates automatically with every code change; signature modifications are instantly reflected.
- **Cognitive Clarity**: Clear structural separation ensures users instantly identify whether a page teaches a skill (Tutorial), solves a problem (How-To), provides facts (Reference), or explains concepts (Explanation).
- **Sub-Second Build Latency**: Strict documentation builds execute in under 5 seconds locally and in CI.

### Negative
- Inter-project cross-linking relies on standard Markdown links rather than Sphinx's `intersphinx` inventory references.
- Script gallery execution is coordinated via dedicated test runners rather than `sphinx-gallery` compilation hooks.
